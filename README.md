# NJFU Wiki 2.0｜校园成长决策与经验协作平台

> 让分散的同校资料与经验，从“能被找到”进一步变成“能帮助学生做判断并开始行动”。

**在线体验：** [打开 Web MVP](https://njfu-wiki-advisor.g1342038753.chatgpt.site)<br>
**产品过程：** [查看需求分析与方案设计 FigJam](https://www.figma.com/board/Uaa8TfAvCXnz7MMvOqjiK3/NJFU-WIKI-2.0?node-id=0-1&t=TWZbfCstcUmpN2bn-1)<br>

## 一句话理解这个产品

NJFU Wiki 2.0 面向南京林业大学计算机学院学生，提供两种获取帮助的方式：

- **知道自己要找什么：**直接搜索课程、竞赛、升学与学习资料。
- **不知道该找什么：**向 AI 描述处境，由系统澄清目标与约束，推荐合适路径、资料和下一步行动。

它不是一个只会给出链接的聊天机器人，也不是把 GitHub 文件搬进网页的资料站。产品以同校资料、经验与规则为信息底座，用 AI 降低“表达需求、判断适用性和开始行动”的门槛，并通过收藏、贡献和反馈形成可持续的校园知识循环。

> 本项目是个人完成的产品探索与工程 MVP，基于对现有 NJFU-WIKI 1.0 内容形态的复盘提出 2.0 方案，不代表南京林业大学或相关学生组织的官方服务。

## 01｜为什么要做 2.0

现有校园 Wiki 已经解决了部分“资料有没有”的问题，但从用户任务出发，仍存在五个断点：

1. **模糊困惑没有入口。** 用户只知道“想保研”“想学 AI”，却不知道应该搜索什么关键词或进入哪个栏目。
2. **找到内容不等于会判断。** 用户很难快速确认资料是否适合自己的年级、基础和目标，来源是否可信、信息是否仍有效。
3. **读完内容不等于能行动。** 文章和外链常成为流程终点，用户仍需自行寻找准备步骤、材料、截止时间和学习顺序。
4. **个性化问题缺少恢复路径。** 静态 Q&A 无法覆盖长尾问题，用户只能反复搜索、进入群聊询问或直接离开。
5. **经验难以持续沉淀。** Markdown 与 GitHub PR 对普通贡献者门槛较高，内容的审核、更新、过期和责任状态也不够透明。

因此，我把问题从“重做一个资料网站”重新定义为：

**如何帮助南林计算机学生从不明确的问题出发，找到可信且适合自己的信息，把它转化为下一步行动，并让这次经验继续帮助后来者？**

## 02｜用户与核心任务

| 用户角色 | 典型处境 | 希望完成的任务 |
| --- | --- | --- |
| 在校学生（核心用户） | 面临方向、课程、竞赛、升学或求职选择 | 找到信息，判断是否适合自己，并知道下一步做什么 |
| 学生与校友（内容供给者） | 手里有资料或经验，但缺少整理与发布方式 | 低成本贡献、补充或纠错，让经验可以被复用 |
| 计协与内容责任人（运营者） | 内容分散且更新依赖个人 | 审核、更新、归档内容，并根据反馈发现问题 |

用户需要的并不只是“更多资料”，而是四种连续价值：

- **方向澄清：**把模糊困惑转化为阶段、目标、约束和起步路径。
- **可信判断：**说明适用人群、前置条件、来源、时效与不适用情况。
- **行动承接：**把内容转化为优先级、准备步骤、材料和近期行动。
- **知识循环：**降低贡献与纠错门槛，让有效经验能够持续更新。

## 03｜产品策略：一套内容，两条发现路径

用户进入“发现”后，系统先尊重他当前的确定程度，而不是强迫所有人都和 AI 对话。

~~~mermaid
flowchart LR
    A[产生问题或目标] --> B{知道自己要找什么?}
    B -->|是| C[关键词搜索 / 分类浏览]
    B -->|否| D[AI 澄清阶段、目标与约束]
    C --> E[可信内容与资料详情]
    D --> F[路径匹配与推荐解释]
    F --> E
    E --> G[下一步行动 / 收藏]
    G --> H[有用、不适用或错误反馈]
    H --> I[内容与推荐持续改进]
    J[学生与校友贡献] --> K[AI 辅助整理]
    K --> L[确认、审核与发布]
    L --> E
~~~

这套方案的差异化不是“多一个 AI 输入框”，而是：

**南林同校语境 × 个体适配 × 可信可追溯 × 行动闭环 × 共建更新**

- 相比泛化经验平台：更强调同校、同阶段、任务化和可验证。
- 相比群聊：把即时但易沉没的回答变成可检索、可复用的公共经验。
- 相比传统 Wiki：从“按栏目阅读”延伸到意图澄清、路径匹配、行动承接和反馈治理。

## 04｜用户侧 MVP

本轮用五个一级页面验证完整但克制的用户链路：

| 页面 | 用户价值 | 当前 MVP 能力 |
| --- | --- | --- |
| 首页 | 理解品牌并进入任务 | 三套视觉主题、一级导航、桌面端响应式 |
| 发现 | 找资料或描述模糊问题 | 搜索结果、资料详情、AI 对话与推荐 |
| 收藏 | 留存并重新找到有用内容 | 本地收藏、文件夹整理与状态保持 |
| 贡献 | 低门槛分享资料或经验 | 资料/经验表单、预览、AI 整理交互 |
| 我的 | 查看个人沉淀 | 用户信息、AI 画像、贡献与收藏入口 |

### 两条关键路径

**路径 A：明确需求**

搜索“数据结构” → 浏览结构化资料卡片 → 查看来源与适用阶段 → 打开原始资料或收藏。

**路径 B：模糊需求**

“我大三，想保研，学过 Python，每周有 10 小时，不知道参加什么比赛” → 系统记录画像 → 只追问真正缺失的信息 → 同时检索竞赛政策与课程资料 → 给出推荐理由、风险、准备周期和行动顺序。

## 05｜AI 在产品中的角色

AI 是建立在内容底座之上的**决策与解释层**，不是事实来源本身。

系统当前使用两个相互独立的知识库：

- **竞赛与政策库：**竞赛类别、适合人群、准备周期、能力要求、综测与推免口径，用于判断“什么更适合”。
- **课程资料目录库：**从 [NJFU-CS/NJFU-Courses](https://github.com/NJFU-CS/NJFU-Courses) 整理出的 365 条资料元数据与原始链接，用于回答“下一步具体看什么”。本项目不复制原仓库中的 PDF、图片等文件。

~~~mermaid
flowchart LR
    A[自然语言问题] --> B[结构化用户画像]
    B --> C{关键信息充分?}
    C -->|否| D[一次追问 1–2 个关键问题]
    D --> B
    C -->|是| E[意图路由与查询扩展]
    E --> F[竞赛政策库 98 个检索块]
    E --> G[资料目录库 365 条资源]
    F --> H[规则匹配与证据排序]
    G --> H
    H --> I[DeepSeek 基于证据生成]
    I --> J[推荐 + 理由 + 风险 + 行动 + 引用]
    H -->|模型失败或限流| J
~~~

关键设计原则：

- 已经知道的信息不重复询问，追问阶段不展示无意义的政策卡片。
- 事实必须来自检索证据；建议与事实分开表达，证据不足时明确承认。
- 推荐数量保持克制，并说明为什么适合、何时不适合。
- 模型不可用、超时或达到公开演示阈值时，回退到规则检索基线。

## 06｜从 Bad Case 推动的产品迭代

| 发现的问题 | 归因 | 迭代结果 |
| --- | --- | --- |
| 用户已经补充信息，系统仍反复追问 | 多轮信息未稳定写入结构化画像 | 持久化会话画像，只询问真正缺失的字段 |
| 追问阶段出现无参考意义的政策卡片 | 没有区分澄清与推荐的展示时机 | 信息不足时隐藏依据卡片，完成判断后再展示 |
| GitHub 文件名包含大量序号，用户看不懂 | 原始文件名被直接当成产品标题 | 增加标题清洗、课程语境与用途摘要 |
| 政策卡片不可点击却呈现为可操作内容 | 证据类型与交互能力不一致 | 政策作为引用依据呈现，资料保留原始链接 |
| 模型接口无返回时体验像系统失败 | 生成层与检索层耦合 | 增加重试、错误提示和确定性回退 |
| 第一轮评测几乎全部通过 | 测试集过于接近已有规则 | 增加歧义、边界、无答案与对抗样本，维护 Bad Case 回归集 |

这些修改来自真实原型验收过程，而不是在完成代码后补写的功能说明。

## 07｜评测：把“感觉不错”变成可回归的问题

评测被拆成三层，分别定位理解、检索和生成问题：

- **用户理解：**画像字段抽取准确率、不必要追问率。
- **知识检索：**Hit@5、Recall@5、MRR@5、Precision@5、Context Precision、nDCG@5。
- **推荐与生成：**忠实度、答案相关性、上下文相关性、推荐适配度、行动性与不确定性表达。

| 层级 | 代表指标 | 当前结果 |
| --- | --- | --- |
| 用户理解 | 字段准确率 / 不必要追问率 | 100% / 0% |
| 检索 | Hit@5 / Recall@5 / MRR@5 | 100% / 73.06% / 0.9194 |
| 检索 | Context Precision@5 / nDCG@5 | 85.43% / 79.38% |
| 生成 | 忠实度 / 答案相关性 / 上下文相关性 | 89.47% / 100% / 93.42% |
| 推荐 | 推荐适配度 / 行动性 | 90% / 94.74% |

> 当前数据来自 30 个检索任务和 19 个生成评审样本，只用于 MVP 回归与问题定位，不代表对所有真实用户问题的泛化表现。

查看[检索评测报告](./evals/results/baseline-v7.md)、[生成评审报告](./evals/results/judge-deepseek-reasoner-v3-final.md)和 [Bad Case 总表](./evals/badcases.jsonl)。

## 12｜本地运行

环境要求：Node.js 22.13 或更高版本、pnpm。

~~~bash
pnpm install
cp .env.example .env.local
pnpm dev
~~~

在 .env.local 中配置服务端模型密钥：

~~~env
LLM_API_BASE_URL=https://api.deepseek.com
LLM_API_KEY=你的服务端密钥
LLM_MODEL=DeepSeek 控制台当前可用的模型 ID
~~~

未配置模型时，界面、画像理解和双库检索仍可通过规则基线运行。

运行构建与评测：

~~~bash
pnpm build
pnpm lint
pnpm eval:baseline
pnpm eval:badcases
~~~

配置真实模型并启动本地服务后，还可以运行：

~~~bash
pnpm eval:generation
pnpm eval:judge
~~~

## 13｜下一步验证

下一轮不优先继续增加页面，而是验证关键假设：

1. 邀请目标用户完成“明确搜索”和“模糊提问”两类任务，观察是否能独立到达有效资料。
2. 增加搜索、追问轮次、推荐点击、原始来源打开、收藏和反馈等关键行为埋点。
3. 重点跟踪“首次有效推荐率、平均澄清轮次、资料打开率、收藏率、无结果恢复率”。
4. 根据真实问题补充路径知识，而不是盲目扩大资料数量。
5. 在验证用户价值后，再接入数据库、真实账号、投稿审核与内容治理。

## 14｜部署与安全

项目可部署到 Vercel。公开演示时，模型密钥只配置在服务端环境变量中，不使用 NEXT_PUBLIC_ 前缀；同时设置请求频率与每日调用软上限。

课程资料链接指向原始 NJFU-Courses 仓库；竞赛、综测和推免信息可能随年份变化，实际决策必须以当届学校及学院官方文件为准。
