# NJFU Wiki｜个人发展与资料推荐 Agent

> 把“我想保研，但不知道参加什么竞赛、该看什么资料”转化为适合用户当前阶段的选择、依据与下一步行动。

NJFU Wiki 是一个面向南京林业大学学生的 AI 产品 MVP。它不是只回答“资料在哪里”，而是先理解学生的年级、目标、已有基础、时间预算和组队情况，再联合检索竞赛政策与课程资料，为目标仍然模糊的用户提供可解释的推荐。

**在线体验：** [打开 NJFU Wiki](https://njfu-wiki-advisor.g1342038753.chatgpt.site)

**项目状态：** MVP 已完成｜真实 DeepSeek RAG 已接入｜检索与生成层评测已建立｜在线演示已发布

![NJFU Wiki 首页预览](./docs/images/njfu-wiki-demo.png)

## 01｜为什么做这个产品

校园资料往往散落在 GitHub、群聊、网盘和经验帖里。真正困难的并不是“搜不到文件”，而是学生还不知道自己此刻应该找什么：

- “我想保研，为了提高综测应该参加哪个竞赛？”
- “大二学过一点 Python，想做人工智能，但不知道先学什么。”
- “这个比赛适合我吗？要准备多久？第一步做什么？”

因此，我将产品目标定义为：**先帮助用户澄清需求，再推荐竞赛与资料，最后给出可以立即执行的行动顺序。**

## 02｜核心体验

1. 用户可以用一句不完整的问题开始，而不需要先填写复杂表单。
2. 系统从多轮对话中持续记录年级、目标、基础、时间预算和组队情况。
3. 仅在影响推荐的信息确实缺失时追问，不重复询问已知信息。
4. 信息充分后，同时检索竞赛政策库和课程资料目录库。
5. 输出推荐理由、风险与取舍、准备周期、能力要求、行动步骤及原始依据。
6. 大模型不可用或达到演示保护阈值时，自动回退到可用的规则检索基线。

## 03｜产品与 RAG 架构

~~~mermaid
flowchart LR
    A[模糊的用户问题] --> B[结构化用户画像]
    B --> C{关键信息充分?}
    C -->|否| D[确定性追问]
    D --> B
    C -->|是| E[查询扩展与意图路由]
    E --> F[竞赛政策库<br/>98 个检索块]
    E --> G[课程资料目录库<br/>365 条 GitHub 资料]
    F --> H[规则推荐基线]
    G --> H
    H --> I[DeepSeek 基于证据生成]
    I --> J[建议 + 行动步骤 + P/R 引用]
    H -->|模型失败或限流| J
    J --> K[评测集与 Bad Case 回归]
~~~

这里刻意区分了两个知识库：

- **决策知识库：** 竞赛类别、适合人群、时间投入、能力要求、综测与推免口径等，用于判断“适不适合”。
- **资料目录库：** 来自 [NJFU-CS/NJFU-Courses](https://github.com/NJFU-CS/NJFU-Courses) 的课程资料元数据与原始链接，用于回答“下一步看什么”。本项目不复制仓库中的 PDF、图片等原文件。

## 05｜关键产品迭代

| 发现的问题 | 原因判断 | 产品与工程改动 |
| --- | --- | --- |
| 用户已经回答，Agent 仍反复追问 | 多轮信息没有稳定写入结构化画像 | 增加会话画像持久化，并只询问真正缺失的字段 |
| 信息补充阶段出现无意义政策卡片 | 检索展示时机没有区分“追问”和“推荐” | 追问阶段隐藏证据卡片，信息充分后再展示 |
| 原始资料名包含大量序号，难以理解 | 直接把 GitHub 文件名当作产品标题 | 增加资料标题清洗与用途摘要层 |
| 模型接口无返回时页面表现像失败 | 生成层与检索层耦合过紧 | 增加重试、错误说明和规则基线回退 |
| 第一版评测几乎全部通过 | 测试集过于接近已有规则 | 增加边界问题、歧义表达、无答案问题和独立模型评审 |

## 06｜评测设计与当前结果

评测不只检查“最终答案像不像”，而是拆成三层：

- **用户信息理解：** 画像字段抽取准确率、不必要追问率。
- **知识库检索：** Hit@5、Recall@5、MRR@5、Precision@5、Context Precision、nDCG@5。
- **推荐与生成：** 忠实度、答案相关性、上下文相关性、推荐适配度、行动性与不确定性表达。

当前回归集结果：

| 层级 | 指标 | 当前结果 |
| --- | --- | --- |
| 用户理解 | 字段准确率 / 不必要追问率 | 100% / 0% |
| 检索 | Hit@5 / Recall@5 / MRR@5 | 100% / 73.06% / 0.9194 |
| 检索 | Context Precision@5 / nDCG@5 | 85.43% / 79.38% |
| 生成 | 忠实度 / 答案相关性 / 上下文相关性 | 89.47% / 100% / 93.42% |
| 推荐 | 推荐适配度 / 行动性 | 90% / 94.74% |

> 这些数字来自当前 30 个检索任务和 19 个生成评审样本，只用于 MVP 回归，不代表对所有真实问题的泛化表现。查看[检索评测报告](./evals/results/baseline-v7.md)、[生成评审报告](./evals/results/judge-deepseek-reasoner-v3-final.md)与 [Bad Case 总表](./evals/badcases.jsonl)。

## 08｜本地运行

环境要求：Node.js 22.13 或更高版本、pnpm。

~~~bash
pnpm install
cp .env.example .env.local
pnpm dev
~~~

在 .env.local 中配置模型；它已被 Git 忽略，不会上传：

~~~env
LLM_API_BASE_URL=https://api.deepseek.com
LLM_API_KEY=你的服务端密钥
LLM_MODEL=DeepSeek 控制台当前可用的模型 ID
~~~

未配置模型时，界面、画像理解和双库检索仍可通过规则基线运行。

## 09｜验证与评测

## 10｜MVP 边界与下一步

- 登录、收藏和贡献目前只保存在浏览器状态中，不是正式账号与权限系统。
- 当前每日模型调用保护是单个服务实例内的软上限；正式开放需要接入持久化限流服务。
- 课程资料链接指向 NJFU-Courses，竞赛、综测和推免结论必须以当届学校及学院文件为准。
- 下一步将补充真实用户可用性测试、行为埋点和基于反馈的推荐策略迭代。

## 11｜部署

项目可部署到 Vercel。需要在服务端配置以下环境变量：

~~~env
LLM_API_BASE_URL=https://api.deepseek.com
LLM_API_KEY=你的服务端密钥
LLM_MODEL=DeepSeek 控制台当前可用的模型 ID
LLM_RATE_LIMIT_PER_MINUTE=6
LLM_DAILY_REQUEST_LIMIT=80
~~~

不要给 LLM_API_KEY 添加 NEXT_PUBLIC_ 前缀。
